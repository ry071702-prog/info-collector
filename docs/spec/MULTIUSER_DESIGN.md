# info-collector 公開パーソナライズ版 — 実現可能性検討 & プランニング

> ⚠️ 本書は **企画・実現可能性の検討ドキュメント**です。本番実装はまだ行いません。
> 「作れるか / いくらかかるか / 何が危ないか / どの順で確かめるか」を判断するための資料。
> 決定の背景は ADR 0003（Obsidian: `ADR/0003-info-collector-公開パーソナライズ版...`）参照。

---

## 1. やりたいこと（ゴール）

個人用の固定フィードを、**誰でも使えるパーソナライズ情報配信サービス**にする。

- ユーザーは自分の興味を選ぶ（例: 「日本のゲーム/アニメ/Disney」「生成AI」「サッカーだけ」）
- そのトピックの情報を集めて **AI が要約・重要度づけ**
- **メール(Gmail)と Discord** でその人向けに通知、サイトでも閲覧
- ログイン: **Google / メールアカウント**

## 2. 前提（確定した方針）

| 項目 | 決定 |
|---|---|
| 対象ユーザー | **全世界の一般人**（非技術者を含む） |
| 情報源 | **YouTube 公式 API + RSS（Google News 検索RSS 含む）+ 自作要約**。**X スクレイピングは使わない**（公開版）。 |
| ジャンル選択 | **共通ジャンルの「カタログ制」**（よくあるジャンルを多数提示して選ばせる）。上級者は任意キーワードも可（BYOK時）。 |
| 収集モデル | **トピック単位の共有収集**（ユーザー単位で集めない） |
| 通知 | **各ユーザー登録メールアドレスへの配信を主**。Discord は任意/後回し（公開版はper-user配信に一手間）。 |
| 認証 | Google / メール |
| AIコストの持ち方 | **ハイブリッド**（無料=operator持ち＋カタログ＋共有 / 上級=BYOK）。詳細は §5.0 |
| コスト方針 | 月額ほぼ0円を維持（超える要因を事前に特定・抑制） |

## 3. 実現可能性の核心：なぜ成立するか

### 3.1 任意ジャンルを安く・合法に集める
- **Google News 検索RSS**: `https://news.google.com/rss/search?q=<キーワード>&hl=ja&gl=JP&ceid=JP:ja`
  → 任意キーワード・任意言語のRSSが**無料で即生成**。「サッカーだけ」も1行で対応可能。
- **YouTube Data API `search.list`**: キーワード動画収集（既存 `youtube_search.py`）。※quota消費に注意（後述）。
- どちらも既存 collector（`rss_generic` / `youtube_search`）を流用でき、新規開発は薄い。

### 3.2 コストをユーザー数に比例させない鍵
**「トピック(ジャンル/キーワード)」をキーに1回だけ収集・要約 → 購読者全員に配る。**

```
ユーザーA: [ゲーム, アニメ]          topic:ゲーム  ──┐
ユーザーB: [ゲーム, サッカー]   →   topic:アニメ  ──┼─→ 各topicを1回収集・要約
ユーザーC: [サッカー, 生成AI]        topic:サッカー ─┤    → 購読者に配信
                                     topic:生成AI  ──┘
```
同じ「サッカー」を100人が選んでも収集・要約は1回。**収集はユーザー数でなく“異なるトピック数”に比例**。

## 4. アーキテクチャ案（既存資産の再利用）

```
[GitHub Actions cron]  ── 既存パイプラインを topic 駆動に拡張
   collectors (youtube_rss / youtube_search / rss_generic / GoogleNewsRSS)
     └─ topic ごとに収集 → 正規化(RawItem)
   processors (classify / 要約)
     └─ topic 単位で重要度づけ + 自作要約（top-N のみ）
   ↓
[Cloudflare D1]  ── users / subscriptions / topics / items / notify_log
   ↓
[Pages Functions]  ── オンボーディング, 認証, 購読管理, フィードAPI
   ↓
[配信] メール(Gmail/送信API) / Discord / サイト表示
```

再利用できるもの: 既存の collector 群・分類/スコアリング・Astro サイト・D1・Pages Functions。
新規に要るもの: 認証、topic/購読データモデル、topic 駆動の収集ループ、per-user 配信、オンボUI。

### データモデル案（D1）
- `users(id, email, auth_provider, created_at)`
- `topics(id, kind[genre|keyword], query, source_pack, created_at)`
- `subscriptions(user_id, topic_id, notify_email, notify_discord, min_importance)`
- `items(id, topic_id, url, title, summary, importance, published_at, dedup_key)`
- `notify_log(user_id, item_id, channel, sent_at)`  ← 重複通知防止

## 5.0 AIコストモデル：ハイブリッド（費用境界＝共有境界）

「あなたのGeminiが青天井で請求される」問題は、**カタログ制 + トピック共有 + ハイブリッドBYOK**で構造的に解決する。

| プラン | 対象 | ジャンル | AIコストを誰が払うか | 通知 |
|---|---|---|---|---|
| **無料（operator持ち）** | 一般人（大多数） | **カタログの共通ジャンルのみ** | **operator（あなた）**。ただし topic 共有で1トピック1回要約 → コストは**カタログ数で頭打ち・ユーザー数非依存** | 日次メール |
| **上級（BYOK）** | パワーユーザー | カタログ＋**任意キーワード** | **本人のGeminiキー**（登録制）。個人専用=共有しない部分は本人負担 | リアルタイム可 |

**設計上のうまみ**: 「安く共有できる部分（カタログ）＝operator持ち」「青天井になりうる部分（任意keyword・リアルタイム）＝BYOK本人持ち」で、**費用の責任分界が共有の境界と一致**する。BYOKキーは既存 slack-emoji-agent の実装パターンを流用可能（暗号化保存・本人のみ使用）。

- カタログ規模の目安: 100〜200ジャンル程度。要約は1日あたり最大でその件数分 → 無料枠圏に収まる。
- BYOKユーザーのカスタムkeywordは per-user 収集・要約（本人キー）。これがコストの青天井部分を吸収する。

---

## 5. コストの正直な見積もりと抑制策

X 除去 + カタログ制 + ハイブリッドの結果、**operator の Gemini コストはカタログ数で頭打ち**（ユーザー数非依存）。BYOKユーザーの任意keyword分は本人キー負担。
operator 視点で**全世界規模になったとき効いてくる真のコストは「メール送信量」**（ユーザー数×配信頻度）。

| コスト要因 | スケール | 誰が負担 | 抑制策 |
|---|---|---|---|
| Gemini（カタログ要約/分類） | **カタログ数で頭打ち**（ユーザー数非依存） | operator | 重要度 top-N のみ要約 / バッチ / 遅延生成 |
| Gemini（BYOK任意keyword） | BYOKユーザーのkeyword数×件数 | **本人キー** | operator負担ゼロ |
| **メール送信** ← 最大の変動費 | **ユーザー数 × 配信頻度** | operator | 日次1通にまとめる / 無料枠内は無料（例 Resend 3,000通/月・100通/日）/ 大規模化時は有料枠 or 収益化 |
| YouTube Data API | search は 1回=100 quota（無料 10,000/日） | operator | RSS 優先、search は人気トピックのみ / 頻度を落とす |
| Google News RSS | 無料 | operator | フェッチ頻度の上限設定 |
| Cloudflare D1/Pages | 行数・リクエスト（無料枠広い） | operator | 保持期間で prune |

**結論**: operator の Gemini は**カタログ数で固定**され青天井にならない。任意keywordの青天井部分はBYOKが吸収。**唯一ユーザー数に比例する変動費はメール送信**で、小規模は無料枠内・大規模化時のみ有料枠 or 収益化が必要。

## 6. リスクと対応（プリモーテム反映）

| リスク | 状態 | 対応 |
|---|---|---|
| X 規約・著作権 | ✅ 解消 | X を公開版から除外。配信は「タイトル+リンク+自作要約」に限定 |
| 需要（他人が使うか） | ❌ **未検証** | **Phase 0 スモークテスト**で先に測る |
| 要約コスト膨張 | ✅ 構造的に解決 | カタログ制でoperator分は頭打ち／青天井部分はBYOK本人負担 |
| メール到達性（全世界規模） | ⚠ 新規 | SPF/DKIM/DMARC設定・二重オプトイン・配信停止リンク必須。スパム判定・バウンス管理 |
| 個人情報保持（グローバル=GDPR等） | ⚠ 新規義務 | プラポリ・退会/削除フロー・最小限保持・地域法（GDPR/CCPA）配慮 |
| BYOKキーの安全保管 | ⚠ | 暗号化保存・本人のみ使用（slack-emoji-agent 実装を流用） |
| Discord 通知の per-user 実現 | ⚠ 後回し | メールを主とし Discord は任意。各自 webhook 登録 or bot DM の摩擦は Phase で後回し |
| 個人運用の運用負荷 | ⚠ | 問い合わせ/障害/モデレーションを最小化する設計（自動化前提） |

## 7. 段階プラン（実装は各フェーズのGoゲート通過後）

> 需要は「あり」と本人判断済み。Phase 0 は任意（確信が強ければ省略、保険なら実施）。

- **Phase 0（任意）— 需要計測**: 公開サイトに「ジャンル選択 + メール登録」オンボUIだけ設置（フェイクドア）。登録数を測る。UIは本実装に流用。
- **Phase 1 — 無料プランMVP**: 共通ジャンル**カタログUI** + Googleログイン + **operator-key で topic共有収集・top-N要約** + **日次メール配信**。Discordは含めない。
  - ここまでで operator コストはカタログ数頭打ち + メール（小規模は無料枠内）。
- **Phase 2 — BYOK上級プラン**: 自分のGeminiキー登録 + カタログ外の任意キーワード + リアルタイム通知。青天井コストを本人キーで吸収。
- **Phase 3 — スケール/収益化**: メール到達性・法対応（GDPR等）整備、メール量が無料枠を超える規模でフリーミアム/広告など収益化。（必要になってから）

## 8. いま出せる結論（Go / Pivot / Stop）

- **技術的実現性: 高**（既存資産流用 + Google News RSS が任意ジャンルの鍵。新規開発は認証・カタログ/購読データモデル・配信層・BYOKに限定）
- **コスト実現性: 高**（カタログ制 + topic共有で operator の Gemini は頭打ち。青天井部分はBYOKが吸収。ユーザー数に比例する変動費はメールのみ＝小規模は無料枠内）
- **法務: 解消済み**（X除外・要約配信に限定）。ただしグローバル展開時はメール到達性と個人情報保護（GDPR等）が新たな要対応。
- **需要: 本人判断で「あり」**。→ **Phase 1（無料プランMVP）から着手可能**。ただし本セッションはプランニングまで、**実装はしない**。
